## Scope

One point-to-point RS232 serial port on IOBOARD: TXD/RXD only, referenced to `GND_LOGIC`
(this port is **not** isolated — already fixed in `power.md`'s isolation table: "RS232 |
No | MAX3232E has no isolation"). No hardware flow control lines (RTS/CTS/DTR/DSR/etc.) —
same reasoning already applied project-wide: this project only ever wired TX/RX for its
UART-based interfaces. No DE/RE — that's an RS485-specific half-duplex control signal,
not applicable here. Not in scope: RS485 (separate subsystem, already complete), PCB
layout, DTE/DCE cable-adapter conventions for whatever gets plugged into the field side.

## Design approach

Four decisions, in the order they were made:

1. **Transceiver: TI MAX3232EIPWR (TSSOP-16, tape & reel, -40 to +85°C), one channel
   used.** Corrected 2026-09-10 from an earlier placeholder "MAX3232EI" that was never a
   real orderable part by itself — it's Texas Instruments' industrial-temp *family
   prefix*, not a buyable SKU (needs a package suffix: EID/EIDB/EIDW/EIPW, each with an
   optional R for tape-and-reel). Landed on TI's part specifically, not Analog
   Devices/Maxim's equivalent (MAX3232EEUE+), because TI's is the one with a ready
   SnapEDA symbol/footprint — practical, not electrical: pinout and function are
   identical either way, same classic second-sourced part. Datasheet switched to match:
   TI's own MAX3232E datasheet, not ADI/Maxim's. The MAX3232E family itself has been the
   standing choice for this project since before this doc existed (`architecture.md`,
   `power.md`) — a 3.3V-native RS232 transceiver, consistent with the `3V3_LOGIC` rail
   everything else on this board runs from. Full datasheet obtained and confirmed
   2026-09-10 ([TI MAX3232E
   datasheet](https://www.ti.com/lit/ds/slls664c/slls664c.pdf)): 16-pin part, two
   independent driver/receiver channels. This design only needs one RS232 signal pair
   (TXD/RXD), so channel 1 (DIN1/DOUT1, RIN1/ROUT1) is used; channel 2 (DIN2/DOUT2,
   RIN2/ROUT2) is left unconnected — same "spare, intentionally left unused" pattern
   already used for the analog subsystem's second op-amp unit.
2. **Charge-pump capacitors: 0.1µF x4, matching the 3.3V±0.3V operating row, plus a
   0.1µF VCC bypass cap.** Re-checked directly against TI's own "Table 3. VCC vs
   Capacitor Values" 2026-09-10: it actually has **three** rows, not two — 3.3V±0.3V
   (C1=0.1µF, C2/C3/C4=0.1µF), 5V±0.5V (C1=0.047µF, C2/C3/C4=0.33µF), and a third "3V to
   5.5V" extended-range row (C1=0.1µF, C2/C3/C4=0.47µF) meant for designs that need one
   fixed cap set across the whole supply range. This board's logic rail is `3V3_LOGIC`
   (3.15-3.45V per the rail's own spec, confirmed already in `power.md`), which sits
   squarely inside the 3.3V±0.3V row (3.0-3.6V) — so the 0.1µF set is still the correct
   pick; the earlier version of this decision just didn't mention the third row existed
   (didn't change which capacitors were selected). Cross-checked against the typical
   operating circuit (TI datasheet Figure 7), which shows C1/C2/C3/C4 all at 0.1µF plus a
   separate 0.1µF `CBYPASS` on VCC — confirms the reservoir caps (what this doc calls
   C2-C4) aren't all one part named "C2"; TI's figure genuinely has three separate
   reservoir/bypass capacitors at that value, matching the 5-capacitor count already used
   on the schematic (C24-C27, C29).
3. **Protection network: none added beyond the transceiver's own on-chip ESD + datasheet
   application circuit.** Considered, and decided against, a dedicated external TVS
   network (the same class of decision RS485 made *in favor of* — see below for why RS232
   comes out differently). Reasoning:
   - The datasheet's own recommended application circuit adds no external protection
     components at all — on-chip ESD alone (±15kV HBM, ±15kV IEC1000-4-2 air-gap, ±8kV
     IEC1000-4-2 contact discharge, all on the RS232 I/O pins) is what the manufacturer
     designed this part to rely on.
   - The receiver inputs are separately rated to ±25V absolute maximum, safe even with
     the part fully unpowered (VCC = 0) — this already covers the great majority of
     realistic miswiring scenarios directly, without needing an add-on component.
   - **Reference-design evidence (2026-09-10):** photos of the reference hardware
     teardown's assembled enclosure show its RS485 subsystem got a dedicated
     protection stage (matches the harsh-environment protection network `rs485.md`
     already selected from the transceiver's own manufacturer reference circuit), but no
     equivalent added protection stage was visible anywhere for the RS232 port — same
     connector-panel footprint, same terminal-block style, no extra populated components
     nearby that would suggest a GDT/TVS/choke network specific to that port. RS485 is a
     bus interface meant for long cable runs near industrial equipment (motors, VFDs,
     contactors) — a genuinely different exposure profile from a short point-to-point
     RS232 link, which is consistent with the two subsystems landing on different
     protection tiers.
   - **Residual risk, flagged rather than silently accepted:** this project reuses one
     Phoenix Contact terminal-block connector family across every subsystem, including
     the 10-30VDC field power input — so a miswired field-power connector landing on this
     3-position RS232 terminal block is physically possible, and the field range's high
     end (up to 30V) exceeds the receiver's ±25V absolute maximum by up to 5V. A TVS
     wouldn't actually close this specific gap well: TVS diodes are pulse-rated
     (transient energy), not continuous-dissipation-rated, so a *sustained* 24-30VDC
     fault would overwhelm a small TVS's continuous power handling in roughly the same
     way it would overwhelm the transceiver's own rating — it would likely fail (ideally
     open, but not guaranteed) rather than indefinitely protect the port. Given that, and
     given the reference design's own apparent choice not to add one here, the mitigation
     for this residual risk is procedural, not componentry: clear panel silkscreen
     labeling per connector position (already this project's practice) rather than an
     add-on part that wouldn't reliably solve the sustained-miswiring case anyway. If a
     real deployment or bench test ever shows this gap actually matters in practice, it's
     revisitable — nothing here is a one-way door (the terminal block's physical footprint
     has room for a future TVS if one gets added later).
4. **Connector: reuse Phoenix Contact MC 1,5/3-ST-3,5 (MPN 1840379), same part already
   used for RS485's connector.** 3 positions: TXD, RXD, GND. 3.5mm pitch, 28-16AWG
   (1.5mm²) screw terminals, through-hole pluggable — matches J1-J5's family for
   BOM/part-count consistency. **Reference-design evidence (2026-09-10):** the reference
   hardware teardown's enclosure connector panel shows RS232 using the same small
   rectangular terminal-block-style cutout as RS485, Analog I/O, and the power input —
   not a D-sub/DB9 shape — confirming a pluggable terminal block, not a DB9 connector, is
   the reference design's actual choice for this port. This resolves the DB9-vs-terminal-
   block fork from this doc's original AskUserQuestion in favor of terminal block, and
   the family/MPN was already locked project-wide, so no new part number is added to the
   BOM baseline (same 1840379 as RS485's connector).

## Step 6: acceptance criteria (confirmed, 2026-09-10)

1. Logic-side operation from `3V3_LOGIC` (3.15-3.45V) draws current within the ~0.3mA
   typ / 1mA max already accounted for in `power.md`'s 3.3V-LOGIC rail sizing — no change
   needed there (already itemized as its own row).
2. TXD/RXD levels meet RS232 spec at the connector: driver output 5-5.4V high / -5 to
   -5.4V low into a 3kΩ load, receiver correctly detects incoming signals per datasheet
   thresholds (VIT- 0.6-1.2V, VIT+ 1.5-2.4V, 0.3V hysteresis).
3. Port survives being driven by another compliant RS232 device presenting the full
   legitimate ±15V signal swing (EIA/TIA-232 spec range) without damage or misdetection —
   covered by the receiver's ±25V absolute-max rating with margin.
4. The residual miswiring gap (field-power's 30V high end vs. the receiver's ±25V
   absolute max) remains a known, documented, non-blocking risk per decision 3 — not
   something this step needs to close, since it was deliberately accepted rather than
   overlooked.
5. Communication is reliable at whatever baud rate the firmware actually configures, up
   to the datasheet's 150kbit/s guaranteed-minimum data rate (the datasheet's 250kbit/s
   figure is the max/best-case column, not a floor — don't design firmware timing against
   250kbit/s as if it were guaranteed) — bench item, can't be closed on paper.

Items 2, 3, and 5 require real hardware to close out fully — Rev-A bring-up.
